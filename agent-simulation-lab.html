Agent Simulation Lab

A lab that takes an AI agent idea from plain English to a tested, scored agent — without writing code. Nine specialist AI agents write the PRD, add domain rules, build the agent, test it against fake copies of the systems it touches, and recommend one next step.

TL;DR

As a PM I kept ideating agents I couldn’t test myself. I built a generic engine with swappable domain packs, so any operations-agent idea can be specified, built, stress-tested and decided on in hours instead of sprints — all on invented data.

Why I built it

Ideas stayed on paper

I could write the PRD, define the logic and argue the business case. But seeing whether an agent actually worked meant waiting for engineering capacity, a test environment and real cases — so most ideas never got tested.

  • Stay in PM mode — I describe the idea and answer questions; I never write code.
  • See the whole loop — the agent picks up work, calls other systems, decides and submits results, exactly as in production.
  • Test the ugly cases — timeouts, half-filled replies, bad inputs and duplicates on demand, with no risk to real systems.
Problem

Operations agents are hard to test safely

Back-office agents have no chat to test through: they pull work from queues and write results back. So most of their bugs surface in production.

PainWhy it happensWho feels it
Testing is riskyA wrong submission writes bad data into a live systemOps teams cleaning up
Edge cases are rareA “not found” or a timeout appears once in thousands of casesEngineers, PMs approving releases
No regression netAfter a logic change there’s no quick proof old cases still passEngineers

Ideas stallWithout a cheap test, ideas wait for capacity or ship on assumptionsThe whole team

Existing tools solve parts of this — some build agents from a spec, others simulate enterprise software. None I found joins spec-to-agent with realistic fakes of the surrounding systems, for a non-engineer.

How it works

Five gated stages, ending in a decision

  1. 01Your idea, in plain EnglishA few sentences — no template and no code.
  2. 02PM agentAsks discovery questions and writes PRD v1.
  3. 03Domain agentAdds labelled domain rules; I approve every assumption, giving PRD v2.
  4. 04Agent Sim LabReview the PRD, build the agent, write scenarios, then test and score — on fake systems and invented data, 20+ scenarios, three repeats each.
  5. 05Report agentWrites the experiment report and recommends one next step.
  6. 06Promote to shadow modeSame code, real settings — only with my approval.
The report decides the loop: a spec problem goes back to the Domain agent, a code problem back to the build, and an idea that can’t reach its goal comes back to me.
The team

Nine agents, one job each

Each agent has one job, a defined set of files it reads and writes, an exit checklist and a list of things it must never do. They hand work over through shared files — never chat memory — so every run leaves a full paper trail.

AgentIts one job

PRD reviewerReads the PRD like a strict engineer: vague steps, conflicts, gaps

Design decisions

Built to keep results trustworthy

  • PRD as source of truth — a failing test is fixed in the PRD and the agent rebuilt; code is never hand-patched.
  • Labelled rules — every assumption needs my approval before a build, so the AI can’t quietly invent business logic.
  • Testers never see the code — scenarios check the spec, not the implementation.
  • Realistic fake systems — fault switches for timeout, error, not found, missing field and malformed replies.
  • Three repeats per scenario — any disagreement is flagged as flaky, never counted as a pass.
  • Same code, test or live — only a settings file differs, so what was tested is what would ship.
  • Generic engine, domain packs — each domain plugs in its fakes, data rules and expert briefing.
Cost

Cheapest model that does the job

3model tiers, matched to each agent’s task
1retry, one tier up, before it asks me
0model calls during test runs — the built agent is rule-based

Checklist work runs on the lightest model, writing and building on the mid tier, and the strongest model only when cheap signals say a job is hard. One command switches the whole lab between economy, balanced and quality modes, and every report shows model usage and where to save next time.

Learning

What I learned

The value isn’t any single agent — it’s the chain. Joining idea-to-PRD and agent sandboxes behind a PM-friendly workflow is what makes ideas testable.
  • Specs fail before code does — vague rules cause most failures.
  • AI reviewers need guardrails — labelled assumptions, isolated testers and evidence-backed verdicts.
  • Cost is a design choice — matching model to task keeps experiments cheap enough to run often.
